You asked for two purpose-named fields rather than reusing notes. Here is the constraint honestly: bd is not ours and has exactly four long-text fields — description, design, notes and acceptance. There is no way to add one called UX design. And design is spoken for: an implementer reads the eight plan headings out of it, and cb-lz5.3 says that format does not change in this trial. So the build design stays in design, and the question is only where the UX design goes.

# Row limit settable from the list pane — the agreed experience

## What a person sees and does

The list pane grows a Rows control at the right of its header, showing the
current limit as a number. Clicking it opens a short menu — 50, 100, 250, 500,
All — and choosing one reloads the list at once. The chosen limit is remembered
for the next visit.

## The states

Empty list    the control still shows, dimmed, reading `Rows 100'.
Still loading the control is dimmed and does not open.
Fewer rows   than the limit: the control reads `Rows 100' unchanged.
Narrow window the control drops to the line below the title.

## The words, exactly

The control reads Rows. The menu entries read 50, 100, 250,
500, All. The empty list reads Nothing to show yet.

## What was considered and rejected

A number the person types. Rejected: every typed value has to be validated
and explained, and the four steps cover what anyone wanted.
Infinite scroll instead of a limit. Rejected: the navigator wants to say how
much is loaded, and scroll position is not a setting they can state.
Remembering the limit per data set. Rejected for now — a later question.

## The mockup

docs/ui/cb-abc-row-limit.html — chosen 2026-09-04, after three rounds.
What C buys. A designer can open, read and edit their own document in an editor or a browser, without ever meeting bd — which is the whole point of writing that agent for a designer. It goes through a pull request, so it is reviewable and has a history. It sits next to the mockup it describes. And neither agent can touch the other's document even by accident.

What C costs. The record is a file rather than a bead field, so a bead and its UX design can go out of step if the pull request is not merged — the agent merges its own documentation pull request, as planners do today, so this is a real but small risk. And bd show alone no longer tells you everything: it gives you the path and you open it.

Option D — the UX design goes in the bead's acceptance field

Everything stays inside bd. acceptance is a field bd already has and this project has never used, so nothing is displaced. It is not called "UX design" — bd show will print the word Acceptance above it, whatever we write in it.
