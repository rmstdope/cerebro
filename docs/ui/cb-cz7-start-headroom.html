cb-cz7 — three ways to stop implementers booting to find nothing

Chosen, 2026-09-04: option A, the headroom cap, with the held row reading → 0 free and the rule landing in both fleet views, held to one case table. Sections B and C are kept as the record of what was rejected and why.

Of 129 implementer passes in decisions.jsonl (2026-08-25 → 2026-09-04), 77 ended within five minutes having claimed nothing. The log shows exactly why: the implementer condition is !planned_ids.is_empty() — a count-blind test, true for every standby builder on the same tick. One planned bead therefore starts as many implementers as the roster has, thirty seconds apart, and all but one boot, run bd ready --claim, find nothing and end.

The planners have the same shape: both boot on buffer 0 of 4 and one finds the planning: label already taken. Below are three ways to fix it. They differ in what the fleet does when there are four planned beads and four idle builders — which is the case that must not get slower.

A — Headroom: start only while there is work nobody is already going for

The condition stops being "is there any work" and becomes "is there work left over". Available work is planned beads − implementers already in flight, where in flight means a session is up and its state file names no bead yet. The 30s peer spacing stays, so four beads still staff four builders, thirty seconds apart. One bead starts exactly one.

What it costs. The standby cell changes from → planned to a count of free beads — → 2 free, → 0 free — which is a new thing to read on the row, and the planner's → buffer<4 gains the same treatment. The in-flight count is read from the fleet rows this view already draws, so nothing new is read from disk. One residual: a builder that came up, claimed, and merged inside the 5s fleet cadence is invisible for one tick — worth one extra start at most, where today it is three.

B — Just widen the spacing: 30s → 120s

One constant. A peer is held for two minutes rather than thirty seconds, which is roughly the observed time from launch to a claim landing on the board. Nothing else changes; the row still reads → planned.

What it costs. It is one line and no new surface, and the log says it would have prevented most of the 77 empty passes. But it is a guess at a latency that varies with how busy Dolt is, it does not fix the planners' own race (a planning: label takes about a minute to reach the remote), and it makes the case we care about — a full queue — four minutes slower. It treats the symptom.

C — Readiness: hold the next peer until the last starter has claimed or given up

Spacing stops being a clock. A peer is held until the last-started builder's state file shows a bead or the word waiting — i.e. until it has actually taken something or actually found nothing — with the 120s clock kept only as a backstop for a session that writes neither.

ONE planned bead — exact, with no count to compute

│◌ Storm       standby     → Cyclops   │
│◌ Rogue       standby     → Cyclops   │

FOUR planned beads — strictly serialised, one boot at a time
00:00  Cyclops    starts
00:50  Storm      starts   (Cyclops's state file named a bead)
01:40  Rogue      starts
02:30  Wolverine  starts

What it costs. The most precise of the three and the slowest to fill a queue: it serialises every start, so a fleet that has just been given four beads staffs itself over two and a half minutes instead of ninety seconds. It also needs a per-name "waiting for" record the view does not keep today.
