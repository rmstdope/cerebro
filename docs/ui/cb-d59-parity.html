Read from GitHub's own CLI command reference, custom-agents reference and hooks reference. The three capabilities the fleet view stands on all exist: a real argv identity (--name NAME, exactly our spelling), custom agents (--agent NAME reading .agent.md files whose required frontmatter is name + description — which every one of our seven agent files already has), and hooks (a preToolUse matcher on the ask_user tool, plus CLI-only notification and permissionRequest). Copilot even reads CLAUDE.md as an instruction file, so the root document needs no second copy.

Question 1 — Forge is opus at xhigh, and Copilot's effort scale stops at high.

Option A — map down, and say so

$ .claude/cerebro/scripts/launch Forge
launch: copilot has no xhigh effort; Forge runs at high

Every role starts on every provider. One line per launch of one role. The mapping lives in agent-cli beside the flag names.

Option B — a Copilot consumer must declare it

$ .claude/cerebro/scripts/launch Forge
launch: agents/architect.md asks for xhigh effort, which copilot does not have - set `architect <model> high' in .cerebro/models.conf before starting Forge

Nothing is silently downgraded; the navigator chooses. Cost: a Copilot consumer cannot start Forge until it edits a file, and the same will be true of every future frontmatter value one provider lacks.

Option C — the frontmatter stops being provider-neutral

agents/architect.md
model: opus
effort: xhigh
effort_copilot: high

Reads honestly and scales badly: every agent file grows a key per provider, and cerebro's own agent definitions start naming providers again — the thing this bead exists to stop.

Question 2 — where does cerebro put Copilot's configuration? Copilot has no --settings: it discovers agents, skills and hooks by path.

Option A — COPILOT_HOME under .cerebro/, set by launch

.cerebro/copilot-home/
  agents/architect.agent.md   -> ../../../.claude/cerebro/agents/architect.md
  skills/plan-bead/           -> ...
  hooks/question-state.json
  settings.json

Untracked, fleet-only, per-consumer. sync-symlinks.sh keeps its promise to write nothing outside the harness's own directories. A human running copilot by hand in the repo is unaffected by the fleet, and unhelped by it.

launch: agent_cli copilot; COPILOT_HOME=.cerebro/copilot-home

Cost: COPILOT_HOME is an env var and never appears in argv, so it cannot be a liveness discriminator — which L2 already made unnecessary. Also: the fleet's login/credentials live under ~/.copilot, so the home has to be seeded or the session is logged out. That is the one thing this option can get wrong, and it is worth the spike proving before anything is built on it.

Option B — the consumer's own .github/, tracked

.github/agents/architect.agent.md   -> ../../.claude/cerebro/agents/architect.md
.github/skills/plan-bead/           -> ...
.github/hooks/cerebro-question-state.json

The path Copilot documents first, and it needs no environment at all. Every human who runs copilot in the repository gets the fleet's agents and skills too — /plan-bead works for a person, not only for a session.

sync-symlinks.sh: linked 7 agents and 6 skills into .github/

Cost: cerebro writes into the consumer's tracked tree for the first time — cb-pq4 deliberately stopped it doing exactly that. Committed symlinks in .github/, and a repository-wide hook file that fires for every copilot run in the repo, fleet or not.
