## The plan specified an EXIT trap that cannot fire where it was placed

**What happened.** The plan's *Files to change* put four `stage="…"` assignments inside
`print_all`, and stated that when the read fails "the subshell's own trap fires and prints the line
before the parent exits". `print_all` runs as `ROWS="$(print_all)"`. Reduced to eight lines and run
on both bash 3.2.57 and bash 5, an EXIT trap installed in the parent does **not** fire in a
command-substitution subshell: exactly one diagnosis line is printed, by the parent, carrying the
stage the *parent* last set. The plan's own test plan then asked the stderr to carry the
declaration's path, which that arrangement could never produce — the two halves of the plan
contradicted each other.
**Why.** Established. Traps are reset to their defaults in a subshell, so the inherited handler is
not run there.
**Cost.** About fifteen minutes: writing the increment-1 test as specified, watching it fail on the
stage word rather than on the missing diagnosis, and reducing the shape to establish which half of
the plan was wrong. No CI cycle.
**Prevent by.** The plan asserted a bash behaviour rather than measuring one, in a repository whose
`tests/lib/consumer.sh` header already documents a *different* surprising trap-and-subshell
interaction it had to measure. `plan-bead` could require that a plan stating what a shell does under
`set -e`, in a subshell, or in a trap says where it was measured — the way this repository's own
comments do.
**Seen before.** none found. `docs/retrospectives/cb-x05.md` mentions subshells, but about parallel
suites rather than trap inheritance.

## A value set inside `$( )` cannot be read by the EXIT trap that needs it

**What happened.** Increment 5 asked `run_launcher_at` to record `_last_launcher="…"` and
`suite_cleanup` to name it on a death. Both were written exactly as specified and the throwaway-suite
test passed. Forcing the *real* `tests/launchers.sh` to die after a launcher run printed nothing:
almost every launcher in that suite runs as `out="$(run_launcher … 2>&1)"`, so the assignment
happens in a subshell and the suite's own shell never sees it. The mechanism worked only in the test
that fabricated its own copy of it — which is the shape the plan chose deliberately, and which is
what hid this.
**Why.** Established. A variable assigned in a command substitution does not reach the parent. The
fix is a file under `$work_dir`.
**Cost.** About twenty minutes, including building a throwaway copy of the suite with a `false`
injected after a launcher run to see the real behaviour. No CI cycle.
**Prevent by.** Two things, both general. A test that fabricates its own copy of the mechanism it is
asserting proves the mechanism and not the caller — `implement-bead`'s *When the plan is wrong*
already says to read a helper before building on it, and this is its analogue for a plan's own test
design. And a diagnostic that only fires on a death is worth firing once on purpose before the PR
opens: injecting `false` into a copy of the suite cost one minute and was the only thing that found
this.
**Seen before.** none found.
