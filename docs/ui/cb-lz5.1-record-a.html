## The agreed experience

The list pane grows a Rows control at the right of its header, showing the
current limit as a number. Clicking it opens a short menu — 50, 100, 250, 500,
All — and choosing one reloads the list at once. The chosen limit is remembered
for the next visit.

Empty list    the control still shows, dimmed, reading `Rows 100'.
Still loading the control is dimmed and does not open.
Fewer rows   than the limit: the control reads `Rows 100' unchanged. It is a
              ceiling, not a promise.
Narrow window the control drops to the line below the title, right-aligned.

The words, exactly: the control reads Rows; the menu entries read
50, 100, 250, 500, All; the empty list reads
Nothing to show yet.

## What was considered and rejected

A number the person types. Rejected: every typed value has to be validated
and explained, and the four steps cover what anyone actually wanted.

Infinite scroll instead of a limit. Rejected: the navigator wants to be
able to say how much is loaded, and scroll position is not a setting they can
see or state.

Remembering the limit per data set. Rejected for now: one remembered value
is what was asked for, and per-set memory is a second question that can be asked
later without undoing this.

docs/ui/cb-abc-row-limit.html — chosen 2026-09-04, after three rounds.

## Sent back to the experience stage

2026-09-06. `All' cannot be built as agreed: the list has no upper bound, and a
data set of two million rows would take the pane several minutes to draw and
roughly a gigabyte to hold. Everything else in the agreed experience stands.

The question to settle: what should `All' do on a data set too large to draw —
refuse with a message, cap silently at some number, or be dropped from the menu?
