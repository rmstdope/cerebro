cb-ykz.3 — what supervision does about a stuck row

Two interview rounds, 2026-09-04. This file is the specification for what the fleet view does about a session that stopped mid-work, in both views. Where this file and the bead's plan disagree, this file is right. It refines nothing about how the row looks: that is cb-ykz.2-stuck-rows.html, and it is unchanged.

A row is stuck when its state is working, its turn has ended, and that has stood past the ceiling — thirty minutes, one number for every role and phase. The session is sitting at a prompt doing nothing, so typing one line into it restarts it, and that is what makes this different from every existing supervision arm.

1. The fact that decides the shape

Typing a line into a session fires the UserPromptSubmit hook, which runs agent-turn resumed and clears the recorded turn-end. So the line always un-sticks the row, whether or not the agent does anything with it; if the agent simply stops again, the Stop hook re-stamps the turn-end and the thirty minutes start over. There is therefore no such thing as "still stuck from the same stretch" — only "stuck again".

2. A stuck interactive role chosen — resume, then end

Xavier, Beast, Cerebro, Moira, Psylocke, Cypher, Forge. Each holds no claim, no worktree and no pull request, so ending one costs a pass and its own trigger starts a fresh session within seconds.

t+30m  stuck. One line typed. `since' on the row reads 09:12Z.
✗ Moira        user-feedbk  sweep                 stuck 30m
[cerebro] Your turn ended while your state file still said you were working…
header: Moira's turn had ended; it was asked to carry on.

t+31m  the typed line cleared the turn-end: an ordinary working row again.
● Moira        user-feedbk  sweep                 3h44 3h44

t+61m  stuck again — AND `since' is still 09:12Z, so between the line landing
       and now the agent wrote nothing at all. The line did not take.
✗ Moira        user-feedbk  sweep                 stuck 30m
       → the session is ended, its buffer kept as the record of the pass,
         and its own trigger starts a fresh one.
◌ Moira        user-feedbk  standby               → 2 issues
header: Moira was stuck and did not answer; its session was ended.

The case that must NOT end: the line took, the agent worked and stopped
again — `since' moved, so this is a first occurrence again and it is
resumed a second time rather than ended.

Under a stop flag the same moment retires it instead: the flag says no further pass, so ending-and-restarting would start the very pass the flag exists to prevent. The flag is cleared with it and the name is disarmed — the shape the waiting arm already has.
Header: Forge was stuck and did not answer; it was retired and its stop flag is cleared.

Rejected: resume once and nothing more — Moira's observed 698 minutes would still have been 698 minutes. End it straight away with no line typed — cheapest to build, and it throws away a pass a single typed line might have finished, transcript and all. A second wall-clock ceiling instead of "the state file never moved" — a second constant in each language, and it fires on a legitimately long unbroken pass that happened to go stuck once near the end of it.

3. A stuck implementer chosen — resume once, and no more

It holds a claim, a worktree and possibly an open pull request. Nothing here ends its session, and if the typed line does not take, nothing further is done about it here.

t+30m  one line typed into the session, once.
✗ Wolverine    implementer  ci          cb-d59.4  stuck 30m
[cerebro] Your turn ended while your state file still said you were working…

t+62m  if it never woke, the escalation that already exists is the one that
       fires: any in_progress bead a live session has not committed to for
       sixty minutes is offered as stalled, and `x' asks before running it.
Sweeps 1
  cb-d59.4 stalled 62m with Wolverine — unclaim?

Rejected: a Sweeps finding of its own — it would list the same bead twice beside the stalled row, because a stuck implementer is precisely one that has stopped committing; and it would be the first sweep computed from the fleet snapshot rather than from a script, so the sweeps table would grow a row that fits none of its columns. Nothing at all — three of the six observed stretches were implementers, and the hours would stay hours.

4. The clock chosen — one number

t+30m  row turns red  and  line typed        — one ceiling, thirty minutes
t+61m  (interactive only) ended, if the state file never moved

One knob rather than two, so the row and the act cannot disagree about what a red row means. Rejected: a quiet window — red at thirty minutes, typed at forty-five — which costs a second constant in each language and a red row that means two different things fifteen minutes apart.

5. The words typed into a stuck session

Two lines, the same implementer/interactive split the existing unanswered-question pair has: an implementer has work it may hand back, an interactive role has none.

implementer
[cerebro] Your turn ended while your state file still said you were working.
If you are waiting on a review sub-agent, say so in one line and go on waiting.
Otherwise do not stop here: write your state file, carry on from where you left
off, or hand the work back for a person to decide exactly as your own
instructions describe, and finish the run.

interactive role
[cerebro] Your turn ended while your state file still said you were working.
Do not stop here: write your state file, carry on from where you left off, or
record where you got to where your own instructions say, and finish the run.

The implementer's line names the review wait because that is the one ended turn that is not a failure — the single documented exception to the never-end-a-turn rule — and this is the only line an implementer ever gets. Neither line names a tracker label, a skill or a bead: the words go into a live session in every consumer, so how work is handed back is the agent's own instructions to state, not the fleet view's. That is the reason the two existing nudge lines already give.
