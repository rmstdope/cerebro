ah-ybsr — where the consumer root travels in argv

The rule needs two things in a session's own command line: --name <Name>, which survives, and a path under this checkout, which no longer does. It used to ride on --settings <root>/.claude/cerebro/hooks/question-state.settings.json; the wrapper rewrites --settings from a path into inline JSON, and the root disappears with it.

I checked my own live command line while writing this: the root appears 0 times. Every other flag the launcher passed came through untouched. So the root has to move to an argument the wrapper leaves alone — the question is which, and one of the candidates you would actually see.
WHAT THE WRAPPER DOES TO THE LAUNCHER'S EXEC — measured, not assumed 
launcher passes:  --agent planner --name Xavier --remote-control Xavier --model opus --effort high
                  --settings /Users/henrikku/repos/atlantis-hud/.claude/cerebro/hooks/question-state.settings.json
                  --permission-mode auto "You are Xavier. Your agent definition (planner) is…"

process carries:  --session-id cf75ef67…  --settings {"preferredNotifChannel":"…","hooks":{…"$CEREBRO_SCRIPTS/agent-asking"…}}
                  --agent planner --name Xavier --remote-control Xavier --model opus --effort high
                  --permission-mode auto "You are Xavier. Your agent definition (planner) is…"
The wrapper hoists its own two flags to the front, rewrites --settings into merged inline JSON, and passes everything else — including the whole trailing prompt — through verbatim. You can tell the settings file was read and merged rather than forwarded, because cerebro's own hook survives inside the blob as the literal unexpanded string $CEREBRO_SCRIPTS/agent-asking. The blob contains no path under the checkout, which is why the rule now fails for every agent.
OPTION 1 — --append-system-prompt carries it (invisible to you) 
exec claude --agent planner --name Xavier --remote-control Xavier \
     --append-system-prompt "This session is Xavier of the cerebro fleet rooted at /Users/henrikku/repos/atlantis-hud/." \
     --settings … --permission-mode auto "You are Xavier. …"
what you see when the terminal opens:

> You are Xavier. Your agent definition (planner) is the whole of your instructions:
  follow it from the top, and start now rather than waiting to be spoken to.

— unchanged. The root is in the system prompt, which is never echoed.
Benefit: takes exactly one value, so it can never swallow a following argument; invisible in your terminal; and the sentence it adds is true and harmless — the agent already knows its own name and repo. Cost: every agent's system prompt grows a line it did not have, and the discriminator now lives in something whose purpose is to talk to the model. A reader tidying prompts could delete it without realising the fleet view depends on it — so it needs a comment saying so, and a test. Preservation by the wrapper is inference (every non-settings flag survived), not proof.
OPTION 2 — the trailing prompt carries it (you see the path) 
exec claude --agent planner --name Xavier --remote-control Xavier --settings … --permission-mode auto \
     "You are Xavier. Your agent definition (planner) is the whole of your instructions: follow it from
      the top, and start now rather than waiting to be spoken to.
      (fleet root: /Users/henrikku/repos/atlantis-hud/)"
what you see when the terminal opens:

> You are Xavier. Your agent definition (planner) is the whole of your instructions:
  follow it from the top, and start now rather than waiting to be spoken to.
  (fleet root: /Users/henrikku/repos/atlantis-hud/)

— an absolute path, in every agent's opening message, in every terminal.
Benefit: the only carrier whose survival is proven rather than inferred — I read my own prompt back out of ps, verbatim, wrapper and all. No new flag, no parsing question. Cost: you read that line every time an agent starts, and it is machine plumbing wearing the clothes of an instruction. It also puts a load-bearing token inside prose that somebody will one day reword.
OPTION 3 — --add-dir carries it  (I tested this and it is dangerous) 
$ claude -p --add-dir /tmp "Reply with exactly: PROMPTSEEN"
Error: Input must be provided either through stdin or as a prompt argument when using --print

$ claude -p --add-dir /tmp --permission-mode auto "Reply with exactly: PROMPTSEEN"
PROMPTSEEN
--add-dir takes <directories…> — variadic. Next to the trailing prompt it ate the entire prompt: the first command ran with no instructions at all. It only survives when another flag sits between it and the prompt. Since the whole premise here is that a wrapper is free to reorder and rewrite arguments, a carrier that silently launches an agent with no instructions if the following flag ever moves is not one I am willing to put under the fleet. Recommended: reject. It goes in the plan's traps so nobody reaches for it again.
