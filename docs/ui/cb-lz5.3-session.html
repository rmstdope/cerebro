cb-lz5.3 — what a build-design session looks like to the developer sitting in it

This agent is the second half of the split. It takes a piece of work whose experience is already agreed — someone else settled that, days ago, with the design agent — and turns it into a plan an implementer can build unattended: architecture, files, increments, tests, verification. Its reader is a software developer, and unlike the design agent it may assume the whole of this repository: beads, worktrees, the gate, the fleet. It talks like a colleague, not like a form.

Three things on this page are yours to agree: whether it asks you anything about the architecture, whether you see the plan before it is filed, and (on the second page) how it sends a piece of work back to the design stage.

Chosen, 9 Sep: A (decides alone), S (files at once) and, on the second page, A (sends back on its own judgement). Round 2 settled the two things those answers left open — there is an opening message, and the pass ends the moment the plan is filed, so the follow-up exchange drawn in Option S below does not happen. See cb-lz5.3-round2.html.

Settled already and not re-opened here: it takes the most urgent agreed-but-undesigned bead itself, one per session, and ends the pass — the same rhythm the planner and the design agent already have.

Question 1 — does it ask you about the architecture?

Today the combined planner decides architecture alone: “Yours: architecture, file layout, which existing code to reuse, the order of increments, the shape of the tests, what is out of scope.” The question is whether splitting the role changes that, now that a developer is sitting there on purpose.

Option A — it decides, and tells you what it decided

The planner's rule, unchanged. No questions at all; the session is a monologue that ends in a plan. Anything it judged two-way is written into the plan's Decided by me, where you can overrule it in a sentence.

Beast

I design the build for work whose look and feel is already agreed.
Today: cb-9f2 — Row limit settable from the list pane.
The design was agreed on 4 Sep; I have read it and the drawing.

Reading the code now — three or four minutes.

... reads src/panes/list.rs, the settings store, two suites ...

Done. The plan is filed.

  3 increments, each opening on a named failing test
  4 files touched, all under src/panes and src/settings
  Reuses SettingsStore::watch rather than a second subscription
  Decided by me: the limit is stored per pane, not globally
                   (the drawing shows two panes at different limits)

  bd show cb-9f2 --json | jq -r .design

>

The cost: a developer who disagrees with the approach finds out by reading the filed plan, and changing it means another pass. The session is over before you have said anything.

Option B — it asks only where the decision is two-way and expensive

It designs alone, and stops at the forks where both answers are defensible and the wrong one costs a rewrite. Batched, with the alternatives spelled out and its own recommendation named. Everything else it decides silently, as in A.

Beast

I design the build for work whose look and feel is already agreed.
Today: cb-9f2 — Row limit settable from the list pane.
The design was agreed on 4 Sep; I have read it and the drawing.

Reading the code now — three or four minutes.

... reads src/panes/list.rs, the settings store, two suites ...

One fork I would rather not settle alone.

  Where the limit lives. The drawing shows two panes at
  different limits, so it is per pane either way — the question is
  the store.

  1. A field on each pane's own state. Simple, no migration;
     the limit is lost when a pane is closed and reopened.
  2. A keyed entry in SettingsStore. Survives a reload, and
     needs a migration for people who already have settings.

  I would take 2 — the drawing's own words are “the way you
  left it”, which reads like it should survive a reload.

> 2, and don't bother migrating - default the missing key

Taking 2, defaulting the missing key. That is the only fork;
writing the plan now.

The cost: the agent has to judge which forks are worth your minute, and it will sometimes get that wrong in both directions — asking about something obvious, or deciding something you cared about. A session where nobody answers has to park the work rather than file a plan.

Question 2 — do you see the plan before it is filed?

The design agent shows its finished record and waits for a yes — you chose that for the UX stage, because the work is queued the moment it is filed. The same argument applies here, and so does the opposite one: a plan is read by an implementer that will refuse anything underspecified, and a wrong plan is cheap to amend.

Option S — filed at once, summarised after

The agent files the plan and reports what it did in a few lines, as in Question 1's mockups. If you want the whole thing you ask for it, or read the bead.

Done. The plan is filed and cb-9f2 is ready for an implementer.

  3 increments, 4 files, reuses SettingsStore::watch
  Decided by me: per-pane storage, missing key defaults to 100

> show me the increments

  1. list_limit_defaults_to_100 — the reader, no UI
  2. limit_control_writes_the_store — the control
  3. limit_survives_a_reload — persistence

>

The cost: a plan you would have changed is already queued, and an implementer may pick it up within seconds. Changing it then means catching it or re-planning.

Option T — shown in full, approved, then filed

The agent prints the plan as the implementer will read it, waits, and files only on a yes. A correction is made and re-shown until you say it is right — the design agent's own step, in a developer's language.

Here is the plan, as the implementer will read it.
Have a look before I file it — after that an implementer may
pick it up within seconds.

  ## Context
  The list pane shows 100 rows and offers no way to change it ...

  ## Files to change, and what to reuse
  src/panes/list.rs — the control, beside the existing filter row
  src/settings/store.rs — one keyed entry, no migration ...

  ## Increments
  1. list_limit_defaults_to_100 ...

  [the whole plan, eight sections]

Is that right?

> increment 2 needs the store test too

Changed — increment 2 now opens on limit_control_writes_the_store
and asserts the store. Anything else?

> no, file it

Filed. cb-9f2 is ready for an implementer.

The cost: one more exchange every session, and a long plan is a screenful. A developer who answers “fine” without reading has approved something unread — and if nobody answers at all, the plan is not filed and the pass ends with nothing queued.

What both options share

Whatever you chooseWhy
It never re-opens a question the design agent settled — not the wording, not the states, not the shape.That conversation happened with a designer, possibly days ago. Re-opening it here is the combined planner under a new name, and it would put two answers on one question.
It never writes the design record, only the plan.Two fields, two owners. The record is the designer's document; the plan is this agent's.
It handles the board, the worktree and the pull request itself.You are a developer, so it may say those words to you — but it does not ask you to run any of them.
One piece of work per session, then the session ends.The rhythm the planner and the design agent already have; a fresh session starts when more work is waiting.
