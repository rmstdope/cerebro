cb-lz5.2 — how a design session opens, and what a designer ever sees of the machinery

The UX agent is written for a designer, who may not be you and who is assumed to know nothing about this repository — not beads, not worktrees, not pull requests. It handles all of that itself. Two things on this page are yours to agree: how a session opens (does the agent pick the work, or offer a choice?) and what the designer sees when the machinery goes wrong.

The word the agent uses for a bead, throughout, is “this piece of work” — never bead, ticket or issue. Overrule that in a sentence if you would rather it said something else.

The question: does the agent pick the work, or offer a choice?

Option A — the agent picks, and says why

The agent takes the most urgent piece of work waiting for a design, exactly as a planner takes the top candidate today, and opens on the subject itself. One piece of work per session.

Ada

I’m the design agent for atlantis. I work out what a change should
look and feel like, we agree it together, and I write it down so
whoever builds it doesn’t have to guess.

Today’s piece of work is the most urgent one waiting for a design:

  Row limit settable from the list pane

  People looking at long lists want fewer rows at a time on a small
  screen, and everything at once on a big one. Right now the list
  always shows 100 rows and there is no way to change it.

I have three questions about the shape of it, and I’ll show you
drawings for each. Ready when you are.

> go on

The cost: the designer never chooses their own work, and a session opens on whatever is most urgent. If they wanted to work on something else, they have to say so unprompted.

Option B — the agent offers what is waiting

The agent lists what is waiting for a design, in the product’s own words, most urgent first, and the designer picks. It still handles everything else.

Ada

I’m the design agent for atlantis. I work out what a change should
look and feel like, we agree it together, and I write it down so
whoever builds it doesn’t have to guess.

Three things are waiting for a design. Most pressing first:

  1.  Row limit settable from the list pane
      Long lists always show 100 rows; there is no way to change it.

  2.  Turn comparison shows a “no changes” dialog on the desktop
      A comparison with nothing in it interrupts instead of saying so quietly.

  3.  Remember the zoom level across reloads
      Reopening the map throws away where you were.

Which one shall we take? (1 is the one the team is waiting on.)

> 2

The cost: one extra exchange before any design happens, every session — and a designer who does not know the work has to choose between three sentences. If nobody answers the choice, the session ends having designed nothing.

The states — where they differ, and where they do not

Nothing is waiting for a design

Identical in both options.

Ada

Nothing is waiting for a design right now — everything that needs one
has had it. I’ll be here when something new comes in.

The piece of work changes nothing a person can see

Identical in both options, and the designer is never asked about it — the agent recognises it, records “nothing a person can see” itself, and moves on. This was already agreed for cb-lz5.1; it is here so you can see what it does to a session.

Ada

(nothing is shown to the designer at all — the session moves straight to
the next piece of work, or ends if there is none)

Nobody answers

Identical in both options. The agent waits, and if the designer never comes back it leaves the question written down for them and stops — the same thing a planner does today.

Ada

I’ll leave this one here — I’ve written down the question and the two
drawings, so we can pick it up exactly where we left off. Nothing is
lost.

The second question: what shows when the machinery fails?

Saving the drawing, recording what we agreed, or reading the list of work can all fail — a network that is down, a change somebody else made first. The designer knows nothing about any of it. What do they see?

Option S — silent: the agent says only what it means for the designer

Ada

That’s the shape agreed — thank you.

I couldn’t finish filing it just now, so I’ve kept everything we
decided and flagged it for the team. Nothing you told me is lost, and
you don’t need to do anything.

No error text, no command, no file path. The detail goes where the team already looks for it. The cost: a designer sitting beside a developer cannot tell them what went wrong.

Option T — one plain sentence, plus the detail underneath

Ada

That’s the shape agreed — thank you.

I couldn’t finish filing it just now: the shared task list wouldn’t
accept the update. I’ve kept everything we decided and flagged it
for the team. Nothing you told me is lost.

Detail for whoever picks this up:
  bd update cb-abc --acceptance ... exited 1
  dolt: remote unreachable (connection refused)

The designer can read the first paragraph and stop; the second is there for whoever they turn to. The cost: the machinery appears in the designer’s session, which is the one thing this role was written to avoid.
