cb-21g — the surface the navigator approved, 2026-09-03

Two rounds. This file is the specification for what the navigator sees while a board write is running — the priority keys (0-4, +, -, u) and x on a sweep finding, the two writes in cerebro-tui. Both run bd and then bd dolt push, and both did it on the thread that draws the screen, so the whole view froze for about a second — thirty on a bad network. Where this file and the bead's plan disagree, this file is right.

1. What was wrong

Every reader in this crate has its own worker thread precisely so a slow subprocess cannot stall the frame. The two writes never got the same treatment: pressing 0 on a bead stopped the clock, the arrow keys and every pane until the remote answered.

2. The line that says it is running

The write moves to its own worker. So that the keystroke is still acknowledged at once, the header's notice slot carries a dim provisional line from the moment the key is pressed, replaced by exactly today's sentence when the write answers. The row itself changes on the very frame the key was pressed (§4).

Rejected: saying nothing until the answer. For x that is a blank header for up to thirty seconds on a slow network, which is indistinguishable from a keystroke that was never received. Also rejected: a single writing… for every path, which says less than the view already knows.

3. Every sentence, verbatim

The provisional lines are dim, use the same words as the finished sentence, and end in an ellipsis. No sentence that ships today changes.

The last line is for a case no keystroke can reach — the worker thread having died. It names the worker rather than bd, which never ran, and it is the write path's counterpart of the reader's the reader thread has stopped.

4. The row changes at once, and never appears to revert

The Work pane re-reads the board every thirty seconds. A read that lands while the write is still running would otherwise show the bead at its old priority. So the requested priority is held over the row from the keystroke until a board read that began after the write settled lands — it is what the row shows, and what it sorts by.

5. The edges

CaseWhat happens
a keystroke while the dim line is upIt survives. Only the answer replaces it — a line that says work is happening stays true while the work is happening. Every other notice is still cleared by the next key.
a second write while one is runningQueued. Writes run in the order they were pressed, one at a time, so nothing is lost or reordered. The row and the dim line show the newest.
an older write answers while a newer one runsIts success does not take the header from the newer write's dim line. A failure always does.
u pressed while a write is still runningIt undoes that write. The undo step exists from the keystroke, not from the answer; a write bd then refuses revokes it.
a failed writeRed in the header and a line in .cerebro/state/errors.jsonl under the context write — the header is painted over by the next frame. A failed push is not a failed write and logs nothing.
q while a write is runningQuits at once. Terminal cleanup stays immediate; an unpushed write is recovered by the next bd dolt push anybody makes.

This is cerebro-tui only. M-x cerebro's own priority keys and x block Emacs the same way and are not touched here.
