cb-op0 — the surface the navigator approved, 2026-09-03

Two rounds. This file is the specification for when a name enters and leaves the armed set — the set that decides whether a row with no session reads standby or dead, and whether a trigger will ever start that name again. Where this file and the bead's plan disagree, this file is right. It follows docs/ui/cb-kcs.4.1-standby-and-starts.html, which specified what a standby row looks like, and docs/ui/cb-kcs.4.2-retry-and-give-up.html, which specified how one stops coming back. Neither said what s does to the set, and the two fleet views answered differently.

1. What was wrong

An agent the navigator started by hand ended its pass cleanly and its row went grey for good. The row is honest about the armed set — the agent simply was not in it, because the Ratatui view's s starts a session without arming, where M-x cerebro arms on every launch. The roster's declaration is read once, as the view comes up, so nothing put the name back.

armed as the view came up, because the roster declares this name standby
│◌ Xavier      standby     → buffer<4  │

f, and then the pass ended — retired, and disarmed. Correct, and unchanged.
│○ Xavier      dead                    │

s — a session runs
│● Xavier      plan        cb-op0      │

the pass ends on `waiting'; the view ends it
│○ Xavier      dead                    │  ← the defect: nothing brings him back

2. Every start arms, whoever asked for it

A launch that succeeds puts the name in the armed set — s, the roster's autostart, and a trigger alike. That is what M-x cerebro has always done, and it is what makes docs/ui/cb-kcs.4.1-standby-and-starts.html §6's promise — "only s brings it back" — true for the first time in the Ratatui view.

s — a session runs, and the name is armed again
│● Xavier      plan        cb-op0      │

the pass ends on `waiting'; the view ends it
│◌ Xavier      standby     → buffer<4  │  ← armed. The trigger starts the next pass.

The cost, taken deliberately. A name the roster never declared is armed too, once it has been started by hand, and the view will keep starting it on its own trigger until k says otherwise. That makes the roster's "omitted means the navigator starts it with s" less literally true. Arming only names the roster declared was drawn and declined: it would have left the two views with different armed sets after the same keystroke, which is the class of divergence this bead exists to close.

a name with no third word in the roster, started by hand, after its pass ends
│◌ Cypher      standby     → PR        │  ← armed now, by that one keystroke

3. Arming is silent

s keeps the two sentences it has and says nothing about the armed set. The blue row after the pass ends is what shows it; a notice saying the same thing a moment earlier was drawn and declined, as was a sentence marking an undeclared name as a one-off.

Cerebro — supervising | Started Xavier. | g refresh | q quit
Cerebro — supervising | Started Xavier, and cleared a stale stop flag. | q quit

4. k means stay gone, at every state

On a standby row k already means disarm (docs/ui/cb-kcs.4.1-standby-and-starts.html §5). On a live session it now means that too: the session is killed and the name leaves the armed set, so nothing starts it again until s does. Without this, killing a mid-bead agent past its own warning got it restarted on the next tick, on the bead the kill had just stranded.

before
│● Cyclops     build       cb-a54      │
k … y
│○ Cyclops     dead                    │
five seconds later, its trigger is still true
│● Cyclops     build       cb-a54      │  ← back, on the bead just stranded

after
│● Cyclops     build       cb-a54      │
k … y
│○ Cyclops     dead                    │
and it stays there
│○ Cyclops     dead                    │  ← only s brings it back

Neither kill prompt changes. Only what follows y does. Adding "and the view will not bring it back" to the mid-bead warning was drawn and declined: it is already the longest sentence in the view, and the rule would then be stated in two places that can drift. f is untouched and keeps its one meaning at every state — it writes the stop flag, and pressing it again clears it.

5. A view that may not act arms nobody

A read-only or draining view holds an empty armed set, so its rows say dead rather than promising a return it cannot perform. The Ratatui view already did this (docs/ui/cb-kcs.4.1-standby-and-starts.html §7); M-x cerebro now does it too, so the same fleet reads the same way in both.

before
  cerebro-tui  Cerebro — read-only: Emacs supervises
                ○ Xavier      dead
  M-x cerebro  Cerebro[read-only: Ratatui supervises]
                ◌ Xavier      standby     → buffer<4  ← a promise it cannot keep

after
  cerebro-tui  ○ Xavier      dead
  M-x cerebro  ○ Xavier      dead                          ← the same thing, both ways round

The consequence is already written down. A view that goes read-only and later takes the lease back comes up with an empty armed set until it is restarted. docs/cerebro-supervision.md step 3 already tells the navigator that of both views; this makes that sentence true rather than adding a caveat to it. Keeping the set while read-only, and having the Ratatui view drop its clear instead, were both drawn and declined.

6. The whole rule, in one table

Nothing else touches the armed set, and both views answer every row the same way.

  what happened                                  the armed set
  the roster declares a name standby              arm      at startup, once
  the roster declares a name autostart            arm      with the launch it does
  a launch succeeds — s, autostart or trigger      arm
  a launch fails                                  unchanged
  a pass ends and the view ends it                unchanged  the point of the set
  a retire — a stop flag, once the pass ends      disarm
  k on a standby row — the disarm prompt         disarm
  k on a live session — the kill prompt          disarm   §4
  five starts produced no pass                    disarm
  a handover — the project declares the other
  view, somebody else holds the lease, or this
  view is draining                                disarm all §5
  this view cannot tell who supervises            unchanged

A recoverable condition may not have a permanent consequence. Emptying the armed set is how a view stops promising sessions it will not start, and that is right when somebody else has or is taking the checkout. It is wrong for the modes that mean I could not find out — an unreadable declaration, a lock error, a declaration the navigator has mistyped: nobody else has the checkout, the next five-second poll recovers, and the armed set does not. In cb-nc8 one transient project-conf failure drained a view for a single tick and left four agents permanently ineligible, replaceable only by pressing s on each. The cost knowingly accepted: during an outage a row can read blue standby while the view could not in fact start it, until the next good poll.

Deliberately not a shared case table. A fixture both implementations answer — the shape of tests/lib/supervise.cases — was drawn and declined: this is the first time the two views have been found to disagree about arming, and this repository earns a mechanical check the second time a class of defect appears, not the first. The rule above is kept by a test on each side that names the other.
