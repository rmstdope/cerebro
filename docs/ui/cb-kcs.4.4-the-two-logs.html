cb-kcs.4.4 — the surface the navigator approved, 2026-09-01/02

Three rounds. This file is the specification for the two append-only JSONL files the Ratatui fleet view writes — every path, every event, every field, every word inside a field, and what the screen says while they are written. Where this file and the bead's plan disagree, this file is right. It changes nothing any earlier file in this family specified: not one row, not one notice, not one key. docs/ui/cb-kcs.4.1-standby-and-starts.html, cb-kcs.4.2-retry-and-give-up.html and cb-kcs.4.3-cadence-rows.html stand exactly as they are.

1. Two files, and they are Emacs's own

<shared root>/.cerebro/state/decisions.jsonl     what the view did, and every trigger it evaluated
<shared root>/.cerebro/state/decisions.1.jsonl   .2, .3 - rotated at 25 MiB, three generations
<shared root>/.cerebro/state/errors.jsonl        a line per thing that went wrong
<shared root>/.cerebro/state/errors.1.jsonl      .2, .3 - the same policy, one setting for both

The same two files M-x cerebro writes, so a navigator who switches supervisor keeps one continuous history and every reader of these files — jq, scripts/fleet-history, the eye — needs no new case. The lease guarantees exactly one supervisor, so the two views can never write at once; and one line is one write(2) on a file opened O_APPEND, which is already what makes this safe beside scripts/agent-state's own writer in the same directory. A separate tui-decisions.jsonl/tui-errors.jsonl pair was rejected: it cannot confuse the two writers, but a cutover then splits one afternoon of one fleet across two files with no line joining them. Nothing on a line says which program wrote it, deliberately — supervisor.json beside them answers that.

2. The vocabulary, and it is closed

eventfields, in this order after event and tsfile

Nine events, not twelve. Emacs's sweep and triage are absent because the Ratatui view does neither: it runs no sweeps, and it types no line into an idle Cerebro. Emacs's own list also carries standby and refused, which no elisp call site emits either. No event outside this table is written, and in particular there is no disarm and no second arm: where a name left the armed set is already readable from the retire or give-up line that put it there. An explicit disarm event, and by:"start" on a re-arm, were drawn and rejected as vocabulary the elisp file never carries, in a file both views write.

3. Every word inside a field

by, on a start: two words, and only two

{"event":"start","ts":"2026-09-02T07:00:01Z","agent":"Cyclops","role":"implementer","reason":null,"by":"navigator"}
   ^ the roster autostarted it as the view came up; nobody pressed anything
{"event":"start","ts":"2026-09-02T07:10:22Z","agent":"Rogue","role":"implementer","reason":"3 planned, unclaimed","by":"trigger"}
{"event":"start","ts":"2026-09-02T07:31:40Z","agent":"Beast","role":"planner","reason":null,"by":"navigator"}
   ^ and this one really was `s'

Byte-parity with the file Emacs has written since May. A third word ("autostart") was drawn and rejected: it would make the same fleet say two different things about one event depending on which view was up, and an autostart is distinguishable anyway — it lands in the first second of a view's life, with an arm line beside it.

reason: the trigger's own phrase, unchanged

"P0 cb-9zz unplanned"     "buffer 2 of 4"        "3 planned, unclaimed"
"2 merged, unverified"    "1 stale verdict"      "4 unranked"

The same six phrases the header notice carries after its em dash (cb-kcs.4.1 section 3, and cb-kcs.4.3's four for the cadence roles). One vocabulary for the screen and the file, so a start seen on screen is findable in the log by its own words.

exit: only for an ending this view did not cause

{"event":"end","ts":"2026-09-02T07:12:11Z","agent":"Rogue","role":"implementer","state":"waiting","bead":null,"stop_flag":null}
... and no `exit' line: this view killed that child itself, and `end' already said so.

{"event":"exit","ts":"2026-09-02T07:14:02Z","agent":"Storm","code":"137","abnormal":true,"last_line":null}
... an exit this view did NOT cause: its own line, with its code.

exit keeps meaning exactly what it means in Emacs's file: something ended that this view did not end. It is also what cb-kcs.3 already decided for the row's verdict column, where a kill this view performed is classified as nothing having gone wrong. A line for every reaped child, with a code of "by-view", was rejected: it would make counting sessions easy at the price of a code value elisp has never written.

4. One evaluate line, in full

{"event":"evaluate","ts":"2026-09-02T07:10:17Z","agent":"Rogue","role":"implementer",
 "reason":null,"planned":3,"planned_ids":["cb-kcs.4.3","cb-kcs.4.2","cb-kcs.4.1"],
 "implementers":4,"p0_unplanned":null,"p4_unranked":0,"merged_unverified":2,
 "stale_verdicts":0,"held_by_guard":true,"spaced_out":null,"spacing":30,
 "backed_off":null,"stop_flag":null,"disarmed":null,"failed_starts":0}

Wrapped here for the page; on disk it is one line. A guard that did not fire is null, never false — that is the elisp shape and a reader depends on it. A nil field is written as null rather than dropped, because "evaluated, and there was no reason" is the answer half these lines carry and a missing key would read as "not evaluated". "held_by_guard":true beside "reason":null is the whole point of the file: it is the only trace of a decision not to start, which is otherwise indistinguishable from a bug.

5. How much of it is written: evaluations, compiled in

verbositylines/daybytes/dayhistory in 4 filesa decision not to start
evaluations — chosen~76,000~25 MiB~4 daysevery tick, with what it read
changes — rejected~900~0.3 MiB~10 monthsonly when the answer changes
decisions — rejected~120~0.02 MiByearsnot at all

Figures measured from this repository's live decisions.jsonl: 3.6 MB and 10,910 lines in 3h26m of a partly-idle fleet, with the other two rows re-counted from that same corpus. It is a constant in the source, with no way to change it — cb-kcs.4.1, .2 and .3 each made every other number a constant for the same reason, and this view has no customisation layer at all. An environment variable defaulting to evaluations was drawn and rejected along with changes: at changes a view that has silently stopped evaluating anything looks exactly like a quiet fleet, where at evaluations the absence of lines is itself the alarm.

6. The error log, and what the screen says about it

The contexts this view writes

{"event":"error","ts":"2026-09-02T07:15:04Z","context":"work","message":"bd: database is locked"}
{"event":"error","ts":"2026-09-02T07:15:09Z","context":"fleet","message":"ps: timed out after 5s"}
{"event":"error","ts":"2026-09-02T07:15:12Z","context":"roster","message":"roster: line 4: unknown word 'autostartt'"}
{"event":"error","ts":"2026-09-02T07:20:00Z","context":"supervise Rogue","message":"Permission denied"}
{"event":"error","ts":"2026-09-02T07:20:41Z","context":"session Storm","message":"exited with code 2: boom"}
{"event":"error","ts":"2026-09-02T07:21:02Z","context":"start Storm","message":"launch: no such file or directory"}
{"event":"error","ts":"2026-09-02T07:21:02Z","context":"supervision","message":"lock error: address in use"}

The two pane contexts are this view's own screen titles, lowercased: fleet and work, so an error names the pane that went red. Borrowing Emacs's panel and beads was rejected — it would buy one jq over the shared file at the price of two words on screen and two different words in the file for the same two things. The four per-name contexts are already identical in both views, and launch <Name> is written by scripts/launch-refused rather than by either view.

A reader that keeps failing: one line per outage

{"event":"error","ts":"2026-09-02T07:15:04Z","context":"work","message":"bd: database is locked"}
... an hour of identical failures, and nothing written for any of them ...
{"event":"error","ts":"2026-09-02T08:14:36Z","context":"work","message":"bd: no such file or directory"}
   ^ a DIFFERENT message is a different fault, so it is written

The work pane re-reads bd every 30 seconds and the fleet pane every 5, so a database locked for an hour is 120 failed reads and the screen shows one red pane throughout. Emacs already does exactly this for a supervision fault — once per distinct message rather than once per tick — for the reason that decides it here: the error log's whole purpose is being short enough to open, and one bad afternoon would bury every other error in it. A line per failed read was rejected, and so was writing nothing at all. The cost, named: the file does not say how long an outage lasted.

The screen is unchanged

┌ Fleet ───────────────────────────────┐

│● Beast       plan        cb-kcs.4.4  │
│○ Storm       dead        nowhere to │

Storm could not be started — nowhere to write this.

This bead adds nothing to any screen. Every error it can write is already visible where it happened — a refused launch is the row's own dead line, a failed read is the pane's failure line, a refused key is its gold notice — and the log is the record that outlives them, not a second announcement. A gold line naming the file (Storm could not be started — see .cerebro/state/errors.jsonl.), once per session, was drawn and rejected: the notice slot is where this view says what it just did, and a filename is not that.

7. While Emacs supervises, this view writes nothing at all

Not a decision, not an error, not a byte. A read-only Ratatui view starts nothing, ends nothing and evaluates no trigger, so it has no decisions to record; and its own reader failures are the same fleet seen through a second window, which would put two accounts of one fleet in one file. It draws them on its own panes and keeps no file. Recording its reader errors anyway was rejected for that reason, and the reason is stronger given section 1: the file it would be writing into is the supervisor's.
