cb-sxf — the surface the navigator approved, 2026-09-01

Two rounds. This file is the specification for what M-x cerebro shows and says about a standby row that has been told to finish. Where this file and the bead's plan disagree, this file is right.

The defect behind it: cerebro--start-due reads no stop flag at all, so a role whose flag was written while it was running, and whose session then died before the poll could retire it — a crash, a k in its own terminal, an Emacs restarted mid-pass — comes back on standby armed and still flagged, and the trigger starts it anyway. It runs a whole pass, and only when it writes waiting at the end of it is the flag finally read. The fix is that the start path skips a flagged name, which is what the Ratatui start path already does.

1. The row names what was done to it, in place of the condition

The fleet, one minute after Beast was told to finish and its session died

Agent          Role          State      Bead       Bead/Phase
◆ Cerebro        orchestrator  idle                  4m
● Xavier         planner       plan       cb-sxf     58s 58s
◌ Beast          planner       standby               ■ told to finish
● Cyclops        implementer   build      cb-kcs.2.2 6m 2m
◌ Rogue          implementer   standby               → planned bead
◌ Psylocke       verifier      standby               → merged, unverified

■ told to finish, plain text, in the Bead/Phase column. Plain like every other label in that column — the ■ the STATE column already carries on a working row is plain too, so this adds no colour and no face. The → is dropped deliberately: it means waiting for, and this row is waiting for nothing. It says what the navigator did rather than what will happen, because that is the half still explicable a day later. ■ stays down and ■ finish; s to resume were both drawn and declined — the first for losing the "you did this", the second for putting a key hint in a column that has never carried one.

It replaces the whole label, including the retry clock. A flagged row is not coming back at all, so ↻ retry in 30s, 3 failed would be as false as → buffer < 4. The flag is the first thing the label answers.

Every kind, not roles only. A standby implementer under a flag is retired by the fleet poll within about one tick, so its row lives roughly five seconds — but it does exist, and for those five seconds the line is true. One rule in one place beat a kind test for a row that lives five seconds.

Three options were declined for this row. Leaving it unchanged (the fix works and is invisible, and the row goes on promising → buffer < 4 while nothing happens); a ■ suffix in the STATE column with the condition kept (no new word, but the For column still names a condition that will not fire); and retiring the row outright the way a flagged standby implementer already is, which needs no new vocabulary at all but diverges from the Ratatui rule.

2. RET on that row

Beast is not running.
You told it to finish, so the view will not start it again.
Press s to start it now, k to leave it down.

The third line is verbatim the line every other standby placeholder already ends with. A variant naming the mechanism — A stop flag is set for it … s clears the flag and starts it — was declined: longer, and "stop flag" is a word from the implementation rather than from the keyboard.

3. s means "keep going" on every row

s clears the stop flag for every kind, not implementers only. Pressing s is a statement that this name should run, so a flag on it is stale — the same argument the navigator already accepted for autostart, which clears a flag for every declared name at M-x cerebro. Without this, s on a flagged role would launch it, it would run exactly one pass, and the flag would retire it again, which is the opposite of what the key was pressed for.

The echo line is unchanged and is the one that already exists:

Beast: cleared a stale stop flag

4. f on a flagged standby row offers to take the flag off

Today f refuses on any standby row. On a flagged one it now does what f does on every other flagged row — the prompt and the confirmation are the ones that already exist:

Stop flag already set for Beast - clear it? (y or n)
Beast will keep going

The row then reads → buffer < 4 again and the trigger starts it. On an unflagged standby row f still refuses with the sentence it has today — Beast is on standby - press k to disarm it, or s to start it now — so f does two things on a standby row depending on the flag. That was accepted: the alternative left f, the key that put the row there, as the one key that could not take it back.

5. What does not change

Nothing changes for a running agent, for k, or for autostart. A working or asking agent under a flag still finishes what it is on and is retired at the end of its pass, and the ■ in its STATE column is untouched.
