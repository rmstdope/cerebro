# cb-92g0 — retrospective

## The Playwright browser lock stayed held with no live holder, and the install hung on it

**What happened.** The first local `bash tests/gate` failed its web console UI leg on
`~/Library/Caches/ms-playwright/__dirlock`, as in cb-6f8f. This time the lock did not clear. After
five minutes of waiting, `ps` showed no Playwright process on the machine, yet the lock directory
was still there. A re-run of `tests/web-console-ui` was killed with SIGTERM inside `playwright
install chromium`. A direct `pnpm exec playwright install chromium` then sat for more than nine
minutes with no output, until it was killed. The lock's mtime moved to the time of the re-run, so
an installer refreshes it while it waits or retries. The leg never ran locally. It passed in CI.

**Why.** Not established. The likely cause is a killed install (by a gate timeout, or by a session
that ended) that left the directory lock behind. Playwright's installer then waits on that lock
without a bound the caller can see.

**Cost.** About twenty minutes: the wait, two hung installs, and a PR opened with one gate leg
unrun locally, relying on CI for it.

**Prevent by** `tests/web-console-ui`: bound the `playwright install` step's wall clock. When it
times out with `__dirlock` present and no `playwright` process alive, name the stale lock on stderr
with the path to remove, rather than hanging. cb-6f8f's "wait and retry within a bound" would not
have cleared this one, because nothing was going to release it.

**Seen before.** cb-6f8f (the same lock, held by a live sibling, cleared on its own). The fleet-*
suite timeouts in this gate run, nine suites at 90s under load, each green when re-run alone, are
already recorded in cb-gyw0 and cb-gkhx.
